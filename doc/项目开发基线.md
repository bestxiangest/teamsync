# TeamSync 项目开发基线

本文档面向后续开发和维护，记录当前 TeamSync 的真实代码边界、模块状态、接口入口、数据库表和优先改造点。

## 当前工程状态

工程组成：

- 后端：`TeamSync`
- 前端：`TeamSync_web`
- 数据库脚本：`doc/sql`
- 文件位置索引：`doc/重点文件位置索引.md`

- Java 21

- MyBatis-Plus
- PostgreSQL
- JWT

- Aliyun OSS

前端技术栈：

- Three.js

## 后端分层

主包：

```text
TeamSync/src/main/java/top/sharpcaterpillar/teamsync
```

核心分层：

- `controller`：HTTP 接口入口
- `service`：服务接口
- `service/impl`：业务实现
- `mapper`：MyBatis-Plus Mapper
- `entity`：数据库实体
- `dto`：请求对象
- `vo`：响应对象
- `config`：Spring MVC、WebSocket、邮件提醒配置
- `interceptor`：登录拦截
- `schedule`：定时任务
- `utils`：JWT、用户上下文等工具

## 前端分层

主目录：

```text
TeamSync_web/src
```

核心分层：

- `api`：前端接口封装
- `views`：业务页面
- `router`：静态路由、动态路由注册、守卫
- `store`：Pinia 状态
- `components`：通用组件
- `hooks`：组合式函数
- `utils/http`：Axios 请求封装
- `utils/socket`：WebSocket 客户端封装
- `types`：全局类型

前端请求工具会把 `POST` / `PUT` 的 `params` 自动转为请求体，因此部分 API 封装看起来传 `params`，实际仍可对应后端 `@RequestBody`。

当前 `TeamSync_web/.env` 默认：

```text
VITE_ACCESS_MODE=frontend
VITE_API_URL=/api
VITE_API_PROXY_URL=http://127.0.0.1:8080
```

前端构建命令按后端接口地址拆分：

- 本地构建：`pnpm build:local`，`VITE_API_URL=http://127.0.0.1:8080/api`
- 生产构建：`pnpm build:prod` 或 `pnpm build`，`VITE_API_URL=/api`，由 Nginx 或部署平台转发到后端

菜单和动态路由有两种模式：

- `frontend`：从 `TeamSync_web/src/router/modules` 加载前端模块路由。
- `backend`：从 `GET /api/v3/system/menus/simple` 读取后端菜单。

当前前端路由维护口径：实际路由入口和模块文件使用 `TeamSync_web/src/router/**/*.js`。同目录同名 `.ts` 文件不会进入当前路由解析链路，后续新增或调整路由时必须改 `.js` 文件，不能只改 `.ts`。`src/router` 下原有同名 `.ts` 路由文件已备份到 `doc/router-ts-backup-20260608.tar` 后从源码目录删除，避免继续误导维护。

当前后端 `MenuController` 只返回仪表盘、项目管理和周期计划兼容入口；系统管理、个人中心等页面文件存在，但切换到 `backend` 模式前需要补后端菜单。

### 已相对完整

- 登录、注册、当前用户
- 用户管理
- 项目和共享分组
- 项目成员和项目内权限
- 看板阶段、任务、拖拽、子任务、评论、活动日志
- 项目文件
- 工作台
- 平台总览
- 日历视图一期：按时间范围聚合任务截止、周期计划下次执行、周期计划本期截止和未读站内通知，可跳转目标页面
- 任务提醒大屏
- 看板任务逾期邮件提醒、任务完成邮件提醒独立开关
- 站内通知中心：任务到期/逾期/完成、周期计划到期/逾期、项目成员变更通知、未读数、已读操作和目标跳转

### 已实现但边界需说明

- 周期计划：独立待办、执行记录和本期手动生成看板任务最小闭环已实现；尚未做周期计划专用定时扫描器。
- 日历视图：前端入口为 `frontend` 路由 `/dashboard/calendar`；如果切到 `backend` 菜单模式，还需要后续在 `MenuController` 补日历菜单入口。
- 周期计划日历截止时间：当前 `pm_recurring_plan` 没有物理 `next_due_time` 字段，接口按 `next_run_at + (due_time - start_time)` 计算，与现有 `RecurringPlanVO.nextDueTime` 口径一致。
- 菜单管理：后端返回硬编码菜单，前端有菜单展示页，但不是数据库持久化菜单。
- 角色管理：前端有页面入口，后端接口和表结构不完整。
- 系统后台入口：前端路由文件存在；后端菜单模式下尚未完整返回这些入口。
- 站内通知中心：站内信写入 `sys_notification`，WebSocket 只推未读数刷新信号，不推完整通知明细；逾期邮件提醒去重仍由 `pm_task_reminder_log` 负责，任务完成邮件只在状态切换事件中按个人开关即时发送。

### 主要风险点

- 配置文件中存在默认或示例敏感配置，部署前必须迁移到环境变量。
- 部分核心关系缺少数据库外键约束，主要靠代码维护一致性。
- 前端路由实际入口是 `.js` 文件；修改路由时不要只改 `.ts`，否则当前运行链路不会生效。
- 周期计划自动生成任务当前只支持本期手动触发，不包含复杂定时扫描和自动批量补偿。

## 周期计划当前边界

周期计划当前核心实体：

- `PmRecurringPlan`
- `PmRecurringPlanAssignee`
- `PmRecurringPlanOccurrence`

当前服务行为：

- 创建计划时写 `pm_recurring_plan` 和负责人关系
- 列表按平台管理员、创建人、负责人做权限过滤
- `autoCreateTask=true` 且配置了项目和阶段时，可通过 `POST /api/recurring-plans/{id}/occurrences/current/generate-task` 为当前本期生成 `pm_task`
- 生成任务时复用 `PmTaskService.createTask`，写入 `pm_recurring_plan_occurrence.generated_task_id`；同一当前本期已有 `generated_task_id` 时直接返回已有任务信息，不重复创建
- 完成本期、跳过本期、延期本期时优先复用已有 `PENDING` 当前执行记录；没有当前执行记录时才按原行为新建一条记录
- 每次处理后推进 `lastRunAt`、`generatedCount`、`nextRunAt`
- 执行记录返回负责人快照、操作人、逾期状态、逾期原因和生成任务 ID；前端可跳转到 `/project/board/:projectId?taskId=...`

当前尚未完成：

- 周期计划专用定时扫描
- 周期计划邮件提醒
- 创建或更新计划时的项目/阶段强绑定校验；当前在生成任务时校验 `stage_id` 必须属于 `project_id`

## 建议开发优先级

### P0：收敛菜单和角色边界

先决定系统后台要不要正式做角色和菜单持久化。若要做，补齐：

- `sys_role`
- `sys_menu`
- `sys_role_menu`
- 角色接口
- 菜单 CRUD
- 前端角色页和菜单页的真实 API
- 后端菜单模式下系统管理入口的返回策略

如果暂时不做，就隐藏或标注未完成入口。

同时要决定前端运行模式：

- 保持 `frontend` 模式：前端路由模块是主口径，后端 `MenuController` 只作为菜单页面或兼容接口。
- 切到 `backend` 模式：后端菜单必须返回完整业务入口，并承担权限裁剪职责。

### P1：打通周期计划生成任务最小闭环

当前已完成手动触发闭环，暂不加定时器：

- `autoCreateTask=true` 时要求选择项目和阶段
- 本期手动生成 `pm_task`
- 写入 `pm_recurring_plan_occurrence.generated_task_id`
- 保证同一期不会重复生成任务
- 前端执行记录能跳转生成任务

### P2：扩展周期计划提醒

决定是否复用 `pm_task_reminder_log`，还是新增周期计划提醒日志。建议独立建表，避免提醒类型混杂。

### P3：补数据库完整性

重点补：

- 项目和用户关系
- 任务和项目 / 阶段 / 创建人关系
- 子任务和主任务关系
- 评论和任务 / 用户关系
- 文件和项目 / 创建人关系
- 任务负责人和任务 / 用户关系
- 任务日志和任务 / 用户关系

周期计划相关表已经有外键，但如果后续生成看板任务，还要继续校验：

- `pm_recurring_plan.project_id` 和 `stage_id` 是否必须同时存在
- `stage_id` 是否属于同一个 `project_id`
- `pm_recurring_plan_occurrence.generated_task_id` 是否需要唯一约束或幂等索引

### P4：清理部署配置

把数据库、邮箱、OSS、JWT 默认配置全部迁出代码仓库，通过环境变量或部署平台密钥注入。
